# Git vs SVN — ответы на вопросы

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

В Git ветка — это просто указатель (файл с хешем коммита, 41 байт), который создаётся мгновенно и не копирует никакие данные: все коммиты и так хранятся в общей базе объектов репозитория. В SVN ветка исторически — это `svn copy` целого каталога `trunk` в `branches/имя-ветки` на сервере. Хотя современный SVN использует дешёвое копирование на стороне сервера, работа с такой веткой (checkout, switch, merge tracking) всё равно требует операций над полным деревом каталогов и обращений к серверу, что медленнее и «тяжелее» локальной операции Git.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

Нет. В SVN нет локального репозитория — рабочая копия хранит только текущее состояние файлов, а вся история находится на центральном сервере. Команда `svn commit` не может завершиться без соединения с сервером, потому что именно сервер присваивает новую ревизию и является единственным источником истории. В Git же коммит — локальная операция (запись в локальный `.git`), а `push` на сервер — отдельный, более поздний шаг.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

- **Очень большие бинарные файлы/монорепозитории**, когда полное клонирование всей истории Git непрактично — в SVN можно сделать checkout только нужной подпапки без скачивания истории.
- **Жёсткий централизованный контроль доступа**, когда нужны точные права на уровне отдельных папок (частая практика в госсекторе и банках).
- **Legacy-инфраструктура**, где вокруг SVN уже построены процессы, интеграции и регламенты, и миграция на Git экономически не оправдана.
- Команды, которым важна **простая линейная модель** без необходимости разбираться в распределённой природе Git.
